# al-folio 使用与维护

优先使用官方页面、数据结构、配置和组件。保留已选择的功能及内容；不要把“简洁”“重构”“清理示例”理解成停用功能或重写原生页面的授权。

## 开始前

1. 读取目标仓库的 `AGENTS.md`、Git 状态、实际 remote 和部署 workflow；保留用户未提交的修改。
2. 读取 `_config.yml`、`Gemfile`、`Gemfile.lock`、涉及的页面 front matter 和数据。把网站内容变更与依赖升级分开判断。
3. 对 regia.me，读取 [本站约定](references/site-contract.md) 和仓库的 `docs/native-feature-audit.md`。以当前仓库和用户最新决定为准；不要把旧 PR 号、提交或路径当作当前状态。
4. 阅读 [官方来源与版本边界](references/official-sources.md)。常规内容修改使用安装版本对应的接口；升级时重新查官方发布说明、配置和插件说明，不凭记忆判断“最新版”。
5. 在涉及功能、页面结构或配置前运行以下基线检查，记录已有问题。将路径变量设为实际位置，不假定某个临时工作目录：

```bash
ruby "$SKILL_DIR/scripts/check_native_features.rb" --root "$REPO"
```

默认策略仅适用于 regia.me。用于其他 al-folio 网站时先根据其明确选择制作独立 `--policy`，不得强加本站域名、导航或功能。

## 按任务读取参考

- 添加或修改内容：读 [内容操作](references/content-recipes.md)。
- 主题/gem/CDN 升级、迁移、覆盖文件或发布：读 [升级与验证](references/upgrades-and-validation.md)。
- 审查、简化页面、删除示例或排查“功能没有出现”：读本站功能审计，按下方流程逐项判定。

## 保留原生能力

把每项差异归入四种状态，分别处理：

| 状态                     | 处理                                                                  |
| ------------------------ | --------------------------------------------------------------------- |
| 已启用且有内容           | 保留入口、数据、布局和交互；验证实际页面                              |
| 已启用但缺少内容         | 保留支持；如仅一篇文章没有分页按钮、没有 preview 图片不显示论文缩略图 |
| 等待账号、素材或构建依赖 | 记录具体缺项；不填示例凭据、不虚构照片/履历、不擅自启用第三方服务     |
| 用户明确不需要           | 保留这一选择及原因；如本站不需要 Projects                             |

- 先清理示例内容，再核对承载功能的页面和组件。不要把原生 Blog/Repo 换成只列标题的 Markdown 循环。
- 保留原生 Blog 的列表、缩略图、元信息、标签/分类/年份归档、置顶入口与分页；修改名称时同时核对导航、permalink、归档、搜索、feed 和旧地址跳转。
- 保留 Repo 的 `github_users`、`github_repos` 和两个原生 repository includes；外部 SVG 卡片失败时保留直接仓库链接。
- 保留 Publications 的 `bib_search.liquid`、bibliography、论文按钮和可选预览；保留 CV 的原生 layout、数据格式和目录。
- 保留站内搜索、深浅色切换、公式、文章目录、图片工具、阅读进度和相关内容的配置。每个功能仍须按其实际全局/页面开关判断，不是所有插件都使用相同门控方式。
- 不以构建成功代替功能验证。原生插件可能在缺少依赖、开关、front matter 或 CDN 配置时静默输出空内容。

按顺序诊断：Gemfile/lock → `plugins:` → 全局开关 → 页面 front matter → 原生调用入口与数据 → CDN URL/SRI → 实际浏览器交互。

## 修改边界

- 优先编辑 `_config.yml`、`_data`、`_pages`、`_posts`、`_news`、`_bibliography` 和用户素材。
- v1.x 的 layout、include、Sass、Liquid tags 和运行时 JS 由 gems 提供。不要编辑 `vendor/bundle` 或复制整套运行时来修复一个配置问题。
- 自建网站可以有必要的本地覆盖；官方 starter 自身禁止运行时目录的规则不能误套到所有用户网站。确需覆盖时说明原因，运行官方 overrides audit/diff，审阅后才 accept，并提交 manifest。
- 改动插件时同步 Gemfile、lock 和 `plugins:`；不要为一次内容编辑执行无关的全部依赖升级。
- 不删除用户原文、历史 permalink 或素材地址。改路由时先查已公开地址并提供有效兼容；Atom/RSS 地址不能用 HTML meta-refresh 冒充 feed。
- 用户明确改变需求时可同步调整本站策略和审计说明；不得为了让检查变绿而删检查、降低标准或修改例外记录。

## 验证与交付

1. 运行静态功能检查。它检查配置、插件、路由和页面连接点，不证明浏览器功能正确。
2. 按改动范围运行仓库规定的格式、官方 upgrade audit、构建、内部链接和浏览器检查。参考升级文档中的实际命令；检查 audit 报告，不能把 `--no-fail` 的零退出码当成零问题。
3. 页面/功能变更时检查受影响页面的桌面和手机、深浅色；实际使用筛选、目录、图库、搜索或公式。外部资源在运行环境被拦截时区分网络限制与站点错误，说明未验证的部分。
4. 内容不足导致的空状态不算删除功能。验证未来能力时可用隔离临时内容；交付前移除测试文章/论文，不发布虚构内容。
5. 保持既有部署方式。检查/推送 PR 不等于已上线；若已有合并/发布授权就继续，否则交付具体可审阅的 PR。不要因本 skill 增设确认步骤。
6. 汇报改了什么、保留了什么、仍需哪些配置、验证结果及当前发布状态。把真实的功能决策更新到仓库审计，避免后续重复猜测。
